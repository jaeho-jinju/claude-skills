# 마무리 사이클 자동화기 (오케스트레이터)

기능 개발이 끝난 변경사항에 대해 **테스트 작성/보강(my-test 위임) → 테스트 실행 → lint(변경 라인만) → 코드 리뷰(로컬 인라인) → 커밋 메시지·커밋(my-commit-comment 위임)** 까지 한 번에 수행합니다. 핵심 작업은 기존 스킬에 위임하고 본 스킬은 흐름을 조율합니다.

## 인자

- 선택 인자로 Jira 티켓 또는 scope 힌트를 받을 수 있습니다. (`my-commit-comment`에 그대로 전달)
  - 예: `/my-step APTS-559`
  - 예: `/my-step fix APTS-559`

## 절차

### Step 0: 사전 점검

1. `git status --porcelain`으로 변경사항 존재 여부를 확인합니다.
   - 변경사항이 0개이면 **"변경사항이 없습니다"** 안내 후 즉시 종료.
2. 변경된 소스 파일 목록을 추출합니다 (스테이징 여부 무관).
   ```bash
   git diff --name-only HEAD -- '*.ts' '*.tsx' '*.js' '*.jsx'
   git ls-files --others --exclude-standard -- '*.ts' '*.tsx' '*.js' '*.jsx'
   ```
   두 결과를 합친 뒤 중복 제거. 이 목록을 **TOUCHED**라고 부릅니다.
3. TOUCHED 중 프로덕션 파일(`__tests__` 외부, `.test.` 미포함)을 **PROD**로, 테스트 파일을 **TEST**로 분리해 둡니다.

### Step 1: 테스트 작성·보강 (my-test 위임)

1. PROD가 비어 있으면 **이 단계를 건너뜁니다** (테스트 파일만 변경된 경우 등).
2. 메인 컨텍스트 보존을 위해 `my-test` 스킬을 호출합니다.
   - 호출 형식 예: `my-test 스킬을 다음 파일들 대상으로 실행: <PROD 목록>`
   - my-test가 내부적으로 `test-writer` 서브에이전트에 위임하므로 본 스킬은 결과 요약만 받습니다.
3. my-test 완료 후 새로 추가/수정된 테스트 파일을 다시 추출하여 **TEST**에 합칩니다.
4. lint는 Step 3에서 PROD + TEST를 합쳐 한 번에 처리하므로 이 단계에서 별도 lint 실행하지 않습니다.

### Step 2: 테스트 실행

1. 변경된 테스트 파일을 대상으로 jest를 실행합니다.
   ```bash
   yarn test --watchman=false --runInBand --findRelatedTests <PROD + TEST 목록>
   ```
   - `--findRelatedTests`로 변경 코드와 연관된 테스트만 빠르게 검증합니다.
   - 테스트 변경량이 크거나 사용자 요청이 있으면 `yarn test:ci` 전체 실행으로 전환 가능.
2. 실패 시 사용자에게 실패 내용을 보고하고 **중단**합니다.
   - 자동 재시도하지 않습니다. 실패 원인 파악은 사용자 결정 영역.
3. 통과 시 자동으로 다음 단계로 이동.

### Step 3: Lint (변경된 라인만) + type-check

> **왜 변경된 라인만인가**: `yarn lint` 전체 실행은 무관한 파일을 자동수정해 blame을 오염시키고 리뷰어가 핵심 변경을 못 찾게 만듭니다. 더 나아가 **변경한 파일 전체에 적용해도 같은 파일 내 무관 라인의 자동수정이 발생**하여 PR diff가 부풀어 오릅니다. lint/format은 **사용자가 실제로 변경한 라인(hunk)에 한정** 적용하여 "의도한 변경 = 커밋된 변경"을 정확히 일치시킵니다.
>
> ⚠️ **`yarn eslint` / `yarn prettier` 사용 금지**: 보닥 프로젝트의 두 yarn 스크립트는 `'./{src,typings}/**/*.{ts,tsx}'` 같은 **고정 glob** 으로 정의되어 CLI 인자를 무시합니다. 실수로 실행하면 코드베이스 전체에 자동수정이 적용되어 무관 파일 수십 개가 변경됩니다(과거 사고 발생). 반드시 `./node_modules/.bin/eslint` / `./node_modules/.bin/prettier` 직접 호출로 변경 파일에 한정하세요. 또한 `.js/.jsx` 파일은 yarn 스크립트 대상에서 제외되므로 직접 호출이 유일한 경로입니다.

1. **사용자 변경 라인 식별** — PROD + TEST 각 파일에 대해 사용자가 실제로 수정한 라인 hunk를 추출합니다.
   ```bash
   git diff -U0 HEAD -- <file>           # 스테이징 여부 무관, HEAD 대비 변경 라인만
   git diff --cached -U0 -- <file>        # 스테이지된 변경
   ```
   - 두 결과의 `+`/`-` 라인 번호를 합쳐 **CHANGED_LINES[file]** 맵을 만듭니다.
   - 신규 파일(`git ls-files --others --exclude-standard`)은 파일 전체가 변경 라인입니다.
2. **lint 실행 전 워킹트리 스냅샷** — 사용자 작업 상태를 보존하기 위해 임시 백업을 만듭니다.
   ```bash
   for f in <PROD + TEST 목록>; do cp "$f" "$f.precommit.bak"; done
   ```
3. **lint·format 실행** — 도구 한계상 파일 단위로 실행합니다 (eslint/prettier는 라인 단위 실행 불가).
   ```bash
   ./node_modules/.bin/eslint --fix <PROD + TEST 목록>
   ./node_modules/.bin/prettier --write <PROD + TEST 목록>
   ```
4. **변경 라인 외 자동수정 되돌리기** — 각 파일에 대해:
   1. lint 적용 후 파일과 백업(`*.precommit.bak`)의 diff를 라인 단위로 추출.
   2. lint diff의 라인 번호가 **CHANGED_LINES[file]** 범위 밖이면 해당 변경을 **백업으로 되돌립니다** (사용자 변경 라인 영역의 자동수정만 유지).
   3. 구현 방식: 백업 파일을 베이스로 하고, lint 결과에서 변경 라인 hunk만 추출하여 백업 위에 patch 적용. 또는 `git checkout HEAD -- <file>` 후 사용자 변경 hunk + lint된 변경 hunk만 다시 적용.
   4. 완료 후 `*.precommit.bak` 파일 삭제.
5. **검증** — `git diff --name-only HEAD`를 확인하여 TOUCHED 외의 파일이 변경되지 않았는지 검사합니다.
   - 무관 파일이 새로 변경됐다면 `git checkout HEAD -- <무관파일>`로 되돌리고 사용자에게 보고합니다.
   - PROD + TEST 파일 내에서도 **CHANGED_LINES 영역 밖이 추가로 변경**됐는지 다시 확인합니다 (4단계 처리 누락 여부 검증).
6. **type-check 실행** — `yarn type-check`를 실행합니다 (type-check는 프로젝트 전체 검증이 자연스러우므로 yarn 스크립트 그대로 사용).
7. **승인 포인트 1** — 다음 중 하나라도 해당하면 사용자에게 보고하고 진행 방향을 묻습니다:
   - eslint 에러가 자동수정으로 해결되지 않고 사용자 변경 라인 안에 남아 있음 (변경 라인 밖의 기존 결함은 별도 이슈로 분류, 본 사이클에서는 통과 처리)
   - prettier가 처리할 수 없는 구문 오류 발생
   - type-check 실패 (변경 라인이 원인인 경우. 기존 결함은 별도 이슈)
   - 변경 라인 외에서 lint 자동수정이 다수 발생하여 자동 되돌리기가 어색해진 경우 (사용자 판단 요청)
   - 모두 통과하면 자동으로 다음 단계 진행 (사용자 확인 불필요).

### Step 4: 코드 리뷰 (로컬 인라인) + 사용자 승인

> **왜 로컬 인라인인가**: `code-review:code-review` 는 PR 기반(`gh pr view`/`gh pr comment` 만 허용) 이라 커밋 이전 단계에서 호출 불가. `simplify`/`security-review` 는 자동 수정 또는 보안 한정이라 본 워크플로우와 부적합. 따라서 본 스킬은 변경 diff 를 서브에이전트에 직접 던져 리뷰 받는 인라인 방식을 채택.

1. **리뷰 대상 준비** — TOUCHED 파일들의 `git diff HEAD` 를 추출합니다 (PROD + TEST 합산).
2. **리뷰 위임** — `general-purpose` 서브에이전트 1개를 호출하여 다음 관점으로 리뷰를 받습니다 (Agent 도구 사용):
   - CLAUDE.md 준수 (특히 "최소한의 변경", "단순함 우선", "발생 불가능한 시나리오 에러 핸들링 금지")
   - 명백한 버그 가능성 (변경 라인 한정, nitpick 제외)
   - 변경으로 인한 미사용 import / 변수 / 함수
   - 변경 의도와 코드의 일치 여부 (사이클 scope·Jira 티켓 인자가 있으면 해당 맥락도 전달)
   - **자동 수정 절대 금지**. 지적 사항만 텍스트로 반환.
   - 프롬프트 끝에 명시: "코드를 수정하지 마라. 파일을 편집하지 마라. 지적 사항만 보고하라."
3. **결과 사용자 보고** — 서브에이전트 응답을 **요약하지 말고** 메인 컨텍스트에 그대로 전달하여 사용자에게 표시합니다.
4. **승인 포인트 2** — 사용자 결정 대기:
   - **OK / 진행** → Step 5 (커밋) 로 이동
   - **지적 반영 요청** → 사용자 명시 지시에 따라 코드 수정 후, 수정 파일에 한해 Step 1(테스트)부터 다시 실행. 자동 반복 금지.
   - **중단** → my-step 종료
   - 본 스킬은 어떤 경우에도 **자동으로 커밋을 진행하지 않습니다**. 명시적 OK 가 있어야만 Step 5 진입.
5. 리뷰 대상이 없는 경우 (변경 파일 0개, Step 0 에서 이미 종료된 케이스) 본 단계는 자동으로 건너뜁니다.

### Step 5: 커밋 메시지·커밋 (my-commit-comment 위임)

1. `my-commit-comment` 스킬을 호출합니다. 인자가 있으면 그대로 전달합니다.
   - 예: `/my-step APTS-559` → `my-commit-comment APTS-559`
2. **승인 포인트 3** — `my-commit-comment` 내부 흐름이 메시지 출력 후 사용자 승인을 받고 `git commit`까지 실행합니다. 본 스킬은 추가 승인을 요구하지 않습니다.
3. 커밋이 거부되거나 메시지 수정 요청이 들어오면 `my-commit-comment`의 표준 흐름에 맡깁니다.

### Step 6: 결과 보고

다음 항목을 한 번에 요약해 사용자에게 보고합니다.

- ✅ Lint·type-check 통과 여부
- ✅ 테스트 작성/보강 결과 (신규 N개, 보강 M개)
- ✅ 테스트 실행 결과 (통과 X / 전체 Y)
- ✅ 코드 리뷰 결과 (지적 N건, 사용자 승인 여부)
- ✅ 커밋 SHA와 한 줄 메시지
- 🔜 다음 추천 액션 (예: `git push`, `/my-mr-write`로 MR 작성)

## 메모

- 본 스킬은 **흐름만** 담당합니다. 구체 규칙은 위임 스킬에 있습니다:
  - 테스트 작성 규칙 → `my-test` → `test-writer` 에이전트
  - 코드 리뷰 → `general-purpose` 서브에이전트 1개 (Step 4 명세대로 인라인 호출)
  - 커밋 메시지 규칙 → `my-commit-comment`
- "기능 개발 단계"는 본 스킬에서 다루지 않습니다. 사용자가 코드를 작성한 뒤 호출하는 마무리 자동화입니다.
- Hook은 사용하지 않습니다. 본 스킬 내부에서 lint를 처리하므로 PostToolUse 자동 lint는 불필요하고, 작업 중간에 무관한 자동수정이 누적되는 위험만 만듭니다.
- 변경사항이 0개일 때 자동 종료, 테스트 실패 시 자동 중단을 기본 정책으로 합니다. 사용자가 매번 차단을 풀어야 하는 흐름은 자동화 가치를 깎습니다.
- 코드 리뷰 단계(Step 4)는 **자동 진행 금지**. 사용자 명시 OK 없이는 절대 Step 5(커밋)로 넘어가지 않습니다.

## 호출 예시

- `/my-step` — 기본 흐름 전체 실행
- `/my-step APTS-559` — Jira 티켓을 scope로 강제
- 자연어: "마무리해줘", "린트하고 테스트 돌리고 커밋까지", "기능 끝났어 정리해줘"
