# 마무리 사이클 자동화기 (오케스트레이터)

기능 개발이 끝난 변경사항에 대해 **lint(touched files만) → 테스트 작성/보강(my-test 위임) → 테스트 실행 → 커밋 메시지·커밋(my-commit-comment 위임)** 까지 한 번에 수행합니다. 핵심 작업은 기존 스킬에 위임하고 본 스킬은 흐름을 조율합니다.

## 인자

- 선택 인자로 Jira 티켓 또는 scope 힌트를 받을 수 있습니다. (`my-commit-comment`에 그대로 전달)
  - 예: `/my-step APTS-559`
  - 예: `/my-step fix APTS-559`

## 절차

### Step 0: 사전 점검

1. `git status --porcelain`으로 변경사항 존재 여부를 확인합니다.
   - 변경사항이 0개이면 **"변경사항이 없습니다"** 안내 후 즉시 종료.
2. 변경된 소스 파일 목록을 추출합니다 (스테이징 여부 무관).
   ```bash
   git diff --name-only HEAD -- '*.ts' '*.tsx' '*.js' '*.jsx'
   git ls-files --others --exclude-standard -- '*.ts' '*.tsx' '*.js' '*.jsx'
   ```
   두 결과를 합친 뒤 중복 제거. 이 목록을 **TOUCHED**라고 부릅니다.
3. TOUCHED 중 프로덕션 파일(`__tests__` 외부, `.test.` 미포함)을 **PROD**로, 테스트 파일을 **TEST**로 분리해 둡니다.

### Step 1: Lint (touched files만)

> **왜 touched files만인가**: `yarn lint` 전체 실행은 무관한 파일을 자동수정해 blame을 오염시키고 리뷰어가 핵심 변경을 못 찾게 만듭니다. 변경한 파일만 fix하면 "의도한 변경 = 커밋된 변경"이 일치합니다.

1. TOUCHED 파일에만 lint·format을 적용합니다.
   ```bash
   yarn eslint --fix <TOUCHED 파일들>
   yarn prettier --write <TOUCHED 파일들>
   ```
   - 파일이 많으면 한 번에 전달. 인자가 너무 길면 분할 실행.
2. 실행 후 `git diff --name-only HEAD`를 다시 확인하여 **TOUCHED 외의 파일이 변경되지 않았는지** 검증합니다.
   - 무관 파일이 새로 변경됐다면 `git checkout -- <무관파일>`로 되돌리고 사용자에게 보고합니다.
3. `yarn type-check`를 실행합니다.
4. **승인 포인트 1** — 다음 중 하나라도 해당하면 사용자에게 보고하고 진행 방향을 묻습니다:
   - eslint 에러가 자동수정으로 해결되지 않고 남아 있음
   - prettier가 처리할 수 없는 구문 오류 발생
   - type-check 실패
   - 모두 통과하면 자동으로 다음 단계 진행 (사용자 확인 불필요)

### Step 2: 테스트 작성·보강 (my-test 위임)

1. PROD가 비어 있으면 **이 단계를 건너뜁니다** (테스트 파일만 변경된 경우 등).
2. 메인 컨텍스트 보존을 위해 `my-test` 스킬을 호출합니다.
   - 호출 형식 예: `my-test 스킬을 다음 파일들 대상으로 실행: <PROD 목록>`
   - my-test가 내부적으로 `test-writer` 서브에이전트에 위임하므로 본 스킬은 결과 요약만 받습니다.
3. my-test 완료 후 새로 추가/수정된 테스트 파일을 다시 추출하여 **TEST**에 합칩니다.
4. 새 테스트 파일에 한해 lint·format을 한 번 더 적용합니다 (Step 1과 동일한 명령, 대상만 새 테스트로 한정).

### Step 3: 테스트 실행

1. 변경된 테스트 파일을 대상으로 jest를 실행합니다.
   ```bash
   yarn test --watchman=false --runInBand --findRelatedTests <PROD + TEST 목록>
   ```
   - `--findRelatedTests`로 변경 코드와 연관된 테스트만 빠르게 검증합니다.
   - 테스트 변경량이 크거나 사용자 요청이 있으면 `yarn test:ci` 전체 실행으로 전환 가능.
2. 실패 시 사용자에게 실패 내용을 보고하고 **중단**합니다.
   - 자동 재시도하지 않습니다. 실패 원인 파악은 사용자 결정 영역.
3. 통과 시 자동으로 다음 단계로 이동.

### Step 4: 커밋 메시지·커밋 (my-commit-comment 위임)

1. `my-commit-comment` 스킬을 호출합니다. 인자가 있으면 그대로 전달합니다.
   - 예: `/my-step APTS-559` → `my-commit-comment APTS-559`
2. **승인 포인트 2** — `my-commit-comment` 내부 흐름이 메시지 출력 후 사용자 승인을 받고 `git commit`까지 실행합니다. 본 스킬은 추가 승인을 요구하지 않습니다.
3. 커밋이 거부되거나 메시지 수정 요청이 들어오면 `my-commit-comment`의 표준 흐름에 맡깁니다.

### Step 5: 결과 보고

다음 항목을 한 번에 요약해 사용자에게 보고합니다.

- ✅ Lint·type-check 통과 여부
- ✅ 테스트 작성/보강 결과 (신규 N개, 보강 M개)
- ✅ 테스트 실행 결과 (통과 X / 전체 Y)
- ✅ 커밋 SHA와 한 줄 메시지
- 🔜 다음 추천 액션 (예: `git push`, `/my-mr-write`로 MR 작성)

## 메모

- 본 스킬은 **흐름만** 담당합니다. 구체 규칙은 위임 스킬에 있습니다:
  - 테스트 작성 규칙 → `my-test` → `test-writer` 에이전트
  - 커밋 메시지 규칙 → `my-commit-comment`
- "기능 개발 단계"는 본 스킬에서 다루지 않습니다. 사용자가 코드를 작성한 뒤 호출하는 마무리 자동화입니다.
- Hook은 사용하지 않습니다. 본 스킬 내부에서 lint를 처리하므로 PostToolUse 자동 lint는 불필요하고, 작업 중간에 무관한 자동수정이 누적되는 위험만 만듭니다.
- 변경사항이 0개일 때 자동 종료, 테스트 실패 시 자동 중단을 기본 정책으로 합니다. 사용자가 매번 차단을 풀어야 하는 흐름은 자동화 가치를 깎습니다.

## 호출 예시

- `/my-step` — 기본 흐름 전체 실행
- `/my-step APTS-559` — Jira 티켓을 scope로 강제
